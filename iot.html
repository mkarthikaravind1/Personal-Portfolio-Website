IoT Task 1

ESP32 Web Server & HTML LED Control

browser click → HTTP GET /on → ESP32 web server → GPIO2 → LED

Objective & Problem Addressed

The goal is to control a physical output (the ESP32's LED) from any browser on the same Wi-Fi network, with no app, no cloud and no extra hardware. Normally, changing the LED means editing code and uploading it again. Here the ESP32 serves its own control page, so anyone on the network can switch it ON or OFF just by opening its IP address.

What is an ESP32 Web Server?

The ESP32 has built-in Wi-Fi and a TCP/IP stack, so it can act as a small HTTP server. Using the WebServer library, it listens on port 80 and links each URL path (a route) to a function in the code. / returns the HTML page, /on turns the LED on, and /off turns it off. server.handleClient() runs in loop() and handles any requests waiting to be processed.

How the ESP32 and Browser Communicate over Wi-Fi

The ESP32 joins the Wi-Fi network in station mode and gets a local IP address from the router (here 192.168.56.226, printed on the Serial Monitor). The laptop is on the same network, so the browser can reach that IP directly. Every click is an ordinary HTTP GET request. The ESP32 runs the matching handler, changes the GPIO, and sends the page back with a 200 OK response.

// Task 1 — ESP32 Web Server & HTML LED Control
// The ESP32 joins the local Wi-Fi, hosts a web page on port 80, and switches
// the onboard LED when the page's ON / OFF buttons request /on or /off.

#include <WiFi.h>
#include <WebServer.h>

const char* WIFI_SSID     = "YOUR_WIFI_SSID";
const char* WIFI_PASSWORD = "YOUR_WIFI_PASSWORD";

#define LED_PIN 2          // Onboard blue LED on the ESP32 DevKit

WebServer server(80);
bool ledState = false;

// The control page. <meta charset="UTF-8"> is required — without it the
// bulb emoji in the heading renders as garbled characters (see Problems).
const char PAGE[] PROGMEM = R"rawliteral(
<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>ESP32 Light Control</title>
  <style>
    body { font-family: Arial, sans-serif; text-align: center; margin-top: 80px; }
    h1   { margin-bottom: 8px; }
    p    { color: #555; }
    .btn { display: inline-block; width: 120px; padding: 14px 0; margin: 12px;
           font-size: 18px; color: #fff; border: none; border-radius: 6px;
           cursor: pointer; text-decoration: none; }
    .on  { background: #2e8b2e; }
    .off { background: #e53935; }
    #state { margin-top: 20px; font-weight: bold; }
  </style>
</head>
<body>
  <h1>&#128161; ESP32 Light Control</h1>
  <p>Control your ESP32 LED</p>
  <a class="btn on"  href="/on">ON</a>
  <a class="btn off" href="/off">OFF</a>
  <div id="state">LED is %STATE%</div>
</body>
</html>
)rawliteral";

void sendPage() {
  String html = PAGE;
  html.replace("%STATE%", ledState ? "ON" : "OFF");
  server.send(200, "text/html; charset=UTF-8", html);
}

void handleRoot() {
  sendPage();
}

void handleOn() {
  ledState = true;
  digitalWrite(LED_PIN, HIGH);
  Serial.println("Request: /on  -> LED ON");
  sendPage();
}

void handleOff() {
  ledState = false;
  digitalWrite(LED_PIN, LOW);
  Serial.println("Request: /off -> LED OFF");
  sendPage();
}

void handleNotFound() {
  server.send(404, "text/plain", "Not found");
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  digitalWrite(LED_PIN, LOW);

  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASSWORD);
  Serial.print("Connecting to Wi-Fi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println();
  Serial.print("Connected. Open http://");
  Serial.println(WiFi.localIP());

  server.on("/", handleRoot);
  server.on("/on", handleOn);
  server.on("/off", handleOff);
  server.onNotFound(handleNotFound);
  server.begin();
  Serial.println("Web server started on port 80");
}

void loop() {
  server.handleClient();
}

HTML Interface for Controlling the LED

The page is stored in flash as a raw string literal (R"rawliteral(...)"). It has a heading, two buttons (green ON and red OFF) and a status line. Before sending, the ESP32 replaces the %STATE% placeholder with the current LED state, so the page always shows the real state.

How the Webpage Sends a Command to the ESP32

  1. User clicks ON. The button is a link to /on, so the browser sends GET http://192.168.56.226/on.
  2. The ESP32 matches the route. server.on("/on", handleOn) sends the request to handleOn().
  3. The GPIO changes. digitalWrite(LED_PIN, HIGH) turns the LED on, and the change is logged over Serial.
  4. The page comes back. The handler returns the HTML with "LED is ON", so the browser shows the new state.

IoT Task 2

Adafruit IO Dashboard & MQTT

dashboard toggle → publish "bulb" → Adafruit IO broker → ESP32 subscriber → relay → bulb

Purpose of Adafruit IO in an IoT System

Task 1 only worked on the local network. Adafruit IO is a cloud IoT platform that removes that limit. It stores device data in feeds, has a drag-and-drop dashboard builder, and runs a public MQTT broker. The ESP32 and the dashboard both connect to Adafruit IO, so the bulb can be controlled from anywhere with internet access, and I didn't have to build any server.

Basic Concept of MQTT

MQTT (Message Queuing Telemetry Transport) is a lightweight publish/subscribe protocol over TCP, made for low-power devices on unreliable networks. Clients never talk to each other directly. A client publishes a message to a topic, and the broker forwards it to every client subscribed to that topic. The headers are small (2 bytes minimum), and the connection stays open with keep-alive pings, so messages arrive almost instantly with no polling.

Publisher, Subscriber & Broker in this Project

Publisher

The Adafruit IO dashboard toggle publishes ON/OFF to the bulb feed. The ESP32 also publishes the confirmed state to bulb-status.

Broker

io.adafruit.com:1883. It authenticates clients with the username and AIO key, then forwards each message to the subscribers of that topic.

Subscriber

The ESP32 subscribes to bulb and switches the relay on every message. The dashboard subscribes to bulb-status to show the real state.

Role of an MQTT Topic / Feed

A topic is the address a message is published to. Adafruit IO calls each topic a feed and also keeps a history of its values. Topics use the format <username>/feeds/<feed-key>. Because of this, the dashboard and the ESP32 only need to agree on the feed name. Neither needs the other's address.

  5. Confirm. The ESP32 publishes ON to bulb-status, and the dashboard indicator updates.

// The ESP32 subscribes to the Adafruit IO feed "bulb" over MQTT. When the
// dashboard toggle publishes ON / OFF, the broker forwards it here and the
// relay switches the bulb. The new state is published back to "bulb-status".
//
// Library: "Adafruit MQTT Library" (Library Manager)

#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

// ================================================
// Wi-Fi
// ================================================
#define WIFI_SSID "YOUR_WIFI_SSID"
#define WIFI_PASS "YOUR_WIFI_PASSWORD"

// ================================================
// Adafruit IO
// ================================================
#define AIO_SERVER     "io.adafruit.com"
#define AIO_SERVERPORT 1883
#define AIO_USERNAME   "YOUR_AIO_USERNAME"
#define AIO_KEY        "YOUR_AIO_KEY"

// ================================================
// RELAY
// ================================================
#define RELAY_PIN 23

// Relay logic
#define RELAY_ON  HIGH
#define RELAY_OFF LOW

WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, AIO_SERVERPORT, AIO_USERNAME, AIO_KEY);

// Feed topics follow the Adafruit IO format: <username>/feeds/<feed-key>
Adafruit_MQTT_Subscribe bulbFeed   = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/bulb");
Adafruit_MQTT_Publish   statusFeed = Adafruit_MQTT_Publish(&mqtt, AIO_USERNAME "/feeds/bulb-status");

// Connects (or reconnects) to the Adafruit IO broker
void connectMQTT() {
  if (mqtt.connected()) return;

  Serial.print("Connecting to Adafruit IO... ");
  int8_t ret;
  uint8_t retries = 5;
  while ((ret = mqtt.connect()) != 0) {
    Serial.println(mqtt.connectErrorString(ret));
    Serial.println("Retrying in 5 seconds...");
    mqtt.disconnect();
    delay(5000);
    if (--retries == 0) ESP.restart();
  }
  Serial.println("Connected!");
}

void setBulb(bool on) {
  digitalWrite(RELAY_PIN, on ? RELAY_ON : RELAY_OFF);
  statusFeed.publish(on ? "ON" : "OFF");
  Serial.println(on ? "Bulb -> ON" : "Bulb -> OFF");
}

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, RELAY_OFF);

  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("Connecting to Wi-Fi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nWi-Fi connected: " + WiFi.localIP().toString());

  mqtt.subscribe(&bulbFeed);
}

void loop() {
  connectMQTT();

  // Wait up to 2 s for a message on any subscribed feed
  Adafruit_MQTT_Subscribe* sub;
  while ((sub = mqtt.readSubscription(2000))) {
    if (sub == &bulbFeed) {
      String value = (char*)bulbFeed.lastread;
      value.trim();
      Serial.println("Received from feed 'bulb': " + value);

      if (value == "ON" || value == "1")       setBulb(true);
      else if (value == "OFF" || value == "0") setBulb(false);
    }
  }

  // Keep the connection alive — Adafruit IO drops idle clients
  if (!mqtt.ping()) mqtt.disconnect();
}

Important Code Sections Explained

  • Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, 1883, …) creates an MQTT client over a plain WiFiClient TCP socket, logging in with the Adafruit IO credentials.
  • Adafruit_MQTT_Subscribe bulbFeed(…"/feeds/bulb") declares the subscription. mqtt.subscribe(&bulbFeed) registers it before connecting.
  • connectMQTT() reconnects whenever the link drops and restarts the board after 5 failed attempts, so a lost connection recovers by itself.
  • mqtt.readSubscription(2000) waits up to 2 s for new messages. lastread holds the payload ("ON" / "OFF").
  • setBulb() drives GPIO23 and publishes the new state to bulb-status, so the dashboard shows what actually happened, not just what was asked.
  • mqtt.ping() keeps the connection alive. Adafruit IO drops clients that stay silent too long.

IoT Task 3

IFTTT + Adafruit IO IoT Automation

"Okay Google, activate Bulb On" → IFTTT applet → Adafruit IO feed → MQTT → ESP32 → bulb

Objective of the IoT Automation

Switch the bulb with a voice command from a phone, without writing any server code. IFTTT connects Google Assistant to Adafruit IO, and the ESP32 from Task 2 receives the result over MQTT.

Basic Concept of IoT Automation

IoT automation means a device acts on its own when an event happens, instead of someone operating it directly. The event can be a voice command, a time of day, a location or a sensor reading. Cloud automation services watch for these events and send commands to devices.

What is IFTTT and Why Use It?

IFTTT ("If This Then That") is a no-code automation service that links hundreds of apps and devices with small rules called applets. It already integrates with both Google Assistant and Adafruit IO, so voice control needs no custom backend, no public IP for the ESP32, and no changes to the Task 2 hardware.

Trigger → Action Concept

Trigger ("If This")

The event IFTTT watches for. Here: Google Assistant: activate scene "Bulb On", said on the phone.

Action ("Then That")

What IFTTT does when the trigger fires. Here: Adafruit: send data to Adafruit IO, which writes ON into the bulb feed.

Role of Adafruit IO

The bridge between IFTTT and the device. IFTTT can't reach an ESP32 on a hotspot, but it can write to a feed. Adafruit IO then pushes that value to the ESP32 over MQTT.

How the Trigger Reaches the IoT System

Google Assistant recognises the phrase and fires the IFTTT trigger. IFTTT calls the Adafruit IO API over HTTPS and stores ON in the bulb feed. Adafruit IO's MQTT broker publishes that new value to every subscriber, which includes the ESP32. The ESP32 then switches the relay. The device is never contacted directly, so no port forwarding is needed.

// IFTTT passes whatever text the applet was configured with, so accept a
// few spellings instead of only an exact "ON" / "OFF".
int parseCommand(String v) {
  v.trim();
  v.toUpperCase();
  if (v == "ON"  || v == "1" || v == "TRUE"  || v.indexOf("TURN ON")  >= 0) return 1;
  if (v == "OFF" || v == "0" || v == "FALSE" || v.indexOf("TURN OFF") >= 0) return 0;
  return -1;
}

void setBulb(bool on) {
  if (on == bulbOn) {
    Serial.println("Bulb already " + String(on ? "ON" : "OFF") + " - ignoring");
    return;
  }
  bulbOn = on;
  digitalWrite(RELAY_PIN, on ? RELAY_ON : RELAY_OFF);
  statusFeed.publish(on ? "ON" : "OFF");
  Serial.println(on ? "IFTTT trigger -> Bulb ON" : "IFTTT trigger -> Bulb OFF");
}

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, RELAY_OFF);

  connectWiFi();
  mqtt.subscribe(&bulbFeed);
}

void loop() {
  connectWiFi();   // recovers if the hotspot drops
  connectMQTT();

  Adafruit_MQTT_Subscribe* sub;
  while ((sub = mqtt.readSubscription(2000))) {
    if (sub == &bulbFeed) {
      String value = (char*)bulbFeed.lastread;
      Serial.println("Feed 'bulb' received: " + value);
      int cmd = parseCommand(value);
      if (cmd == -1) Serial.println("Unknown command - ignored");
      else setBulb(cmd == 1);
    }
  }

  if (!mqtt.ping()) mqtt.disconnect();
}

Problems & Solutions

Problem: There was a delay of a few seconds between speaking and the bulb switching.

Solution: The MQTT path itself is instant. The delay comes from IFTTT processing the applet. That's acceptable for lighting, and I documented it as a limitation of free-tier cloud automation.

Problem: An earlier attempt sent IFTTT webhooks straight to the ESP32's local IP, and they never arrived.

Solution: IFTTT runs in the cloud and can't reach a private 192.168.x.x address. Using Adafruit IO as the middle step means the ESP32 connects out to the broker, so nothing has to connect in to it.

Problem: IFTTT sometimes sent the value with extra spaces or different capital letters.

Solution: parseCommand() trims the text, converts it to upper case, and accepts ON/1/TRUE and OFF/0/FALSE.

What I Learned about Cloud-Based Automation

Cloud automation is mostly about connecting services, not writing code. The firmware hardly changed from Task 2. What changed was who publishes to the feed. Each extra service makes things easier to build, but also adds some delay and another account that can fail.

Reflection

The key idea was separating the trigger from the device. Because the ESP32 listens to a feed and not to a particular sender, any source (a dashboard, a voice assistant, a schedule) can control it with no firmware changes.

Firebase IoT Monitoring Dashboard

Objective of the Firebase IoT Monitoring System

Build my own cloud dashboard with a login, hosted at iot-dashboard-karthik.web.app. Only signed-in users can see readings or switch the bulb. Commands and readings go through a Firebase database instead of a third-party dashboard.

Concepts

Cloud Computing

Cloud computing means using computing resources (servers, storage, databases, software) over the internet, when you need them, and paying for what you use, instead of owning and running the hardware yourself. The provider handles uptime, scaling and maintenance.

IaaS, PaaS, SaaS & BaaS

IaaS: Infrastructure as a Service

Rented virtual machines, storage and networks. You manage the OS and everything above it. e.g. AWS EC2, Google Compute Engine.

PaaS: Platform as a Service

A managed runtime. You deploy code and the platform runs it and scales it. e.g. Heroku, Google App Engine.

SaaS: Software as a Service

A finished application used through the browser. You manage nothing. e.g. Gmail, Adafruit IO, IFTTT.

BaaS: Backend as a Service

Ready-made backend features (database, authentication, hosting, storage) used through SDKs, so an app needs no server code. e.g. Firebase, which this task uses.

What is a Cloud Platform?

A cloud platform is a provider's full set of services under one account and console, for example Google Cloud, AWS or Azure. Firebase runs on Google Cloud. One Firebase project gave me Hosting, Authentication and Cloud Firestore, all linked together.

What is a Database?

A database is an organised store of data that can be searched and updated efficiently and shared safely by many users. Relational databases (MySQL) use tables with a fixed schema. NoSQL databases store flexible documents or key–value data. That suits IoT readings well, because different devices can send different fields.

Firebase Database (Realtime Database & Cloud Firestore)

Firebase offers two NoSQL databases. The Realtime Database stores everything as one big JSON tree and syncs changes to connected clients in milliseconds. Cloud Firestore is the newer one. It stores data as documents inside collections, supports richer queries (sorting, limits), and has the same live updates through onSnapshot. I used Cloud Firestore (region asia-south1, real-time updates enabled), because Task 5's history needs queries like "newest 50 entries sorted by timestamp".

What is a Cloud-Based Dashboard?

A web page, hosted online, that shows live device data and sends commands. It works from any browser and needs no installation. Because it reads from the cloud database and not from the device, it keeps working when the user and the device are on different networks.

Authentication & the Purpose of a Login System

Authentication proves who a user is. Without a login, anyone who found the URL could switch someone's appliances. Firebase Authentication checks the email/password (or Google account) and gives the browser a signed ID token. Every database request carries that token. The ESP32 signs in with its own device account in the same way.

DHT11 Temperature & Humidity Monitoring

Every 2 s the ESP32 reads the DHT11. If a reading fails, it keeps the last good value (the DHT11 sometimes returns NaN). Every 5 s it writes the values to sensors/current. The dashboard's temperature and humidity cards update live through onSnapshot. In the screenshot below they show 24 °C and 52 %.

LDR-Based Light Level Monitoring

The LDR module's analog output goes to GPIO34 (an ADC1 pin, because ADC2 can't be used while Wi-Fi is on). With this module, a lower reading means a darker room. The firmware averages 10 samples per reading to smooth out ADC noise. The value is shown on the Ambient Light card.

Manual Bulb Control

In Manual mode, the dashboard's Turn ON / Turn OFF button writes bulbState to control/device. The ESP32 reads it every 2 s and sets the relay to match.

Automatic Bulb Control using the LDR

In Automatic mode the ESP32 ignores the manual command and decides from the light level. The dashboard disables the bulb button so the two modes can't conflict. The threshold is set from the dashboard (Save Threshold), so it can be retuned for a different room without uploading new firmware.

Logic Used for Automatic Lighting

  • darkLimit = threshold − 50 and brightLimit = threshold + 50. With threshold 500 they are 450 and 550.
  • LDR below 450 → dark → bulb ON. LDR above 550 → bright → bulb OFF.
  • Between 450 and 550 nothing changes. Without this gap, a reading hovering around 500 made the relay click on and off quickly.

LDR Threshold / Calibration Method

  1. Upload the calibration sketch (ldr_calibration.ino), which prints the raw value every 250 ms.
  2. Measure both extremes. Note the reading with the room lights on, then with the sensor covered. Covered, it read 0–19.
  3. Pick the middle. Choose a threshold between the dark and bright readings (500), and leave ±50 as a dead band.
  4. Save it from the dashboard, so it's stored in control/device.threshold and the ESP32 applies it within 2 s.

void setBulb(bool on) {
  bulbState = on;
  digitalWrite(RELAY_PIN, on ? HIGH : LOW);
}

void readControl() {
  if (!Firebase.Firestore.getDocument(&fbdo, FIREBASE_PROJECT_ID, "", "control/device", "")) {
    Serial.println("Control read failed: " + fbdo.errorReason());
    return;
  }
  FirebaseJson json;
  FirebaseJsonData d;
  json.setJsonData(fbdo.payload());

  json.get(d, "fields/mode/stringValue");
  if (d.success) mode = d.stringValue;
  json.get(d, "fields/bulbState/booleanValue");
  if (d.success) manualCmd = d.boolValue;
  json.get(d, "fields/threshold/integerValue");      // Firestore sends integers as strings
  if (d.success) threshold = d.stringValue.toInt();
  else {
    json.get(d, "fields/threshold/doubleValue");
    if (d.success) threshold = (int)d.doubleValue;
  }
}

void applyLogic() {
  int darkLimit = threshold - HYSTERESIS;
  int brightLimit = threshold + HYSTERESIS;

  if (mode == "automatic") {
    Serial.printf("Mode: AUTOMATIC | LDR: %d | darkLimit: %d | brightLimit: %d | Threshold: %d\n",
                  ldrValue, darkLimit, brightLimit, threshold);
    if (ldrValue < darkLimit && !bulbState) {
      setBulb(true);
    } else if (ldrValue > brightLimit && bulbState) {
      setBulb(false);
    }
    Serial.println(bulbState ? "Dark detected → Bulb ON" : "Bright → Bulb OFF");
  } else {
    if (manualCmd != bulbState) setBulb(manualCmd);
    Serial.printf("Mode: MANUAL | Bulb: %s\n", bulbState ? "ON" : "OFF");
  }
}

// Fills the shared field set used by sensors/current and readings/*.
// The threshold is only stored on sensors/current.
void fillFields(FirebaseJson& c, bool withThreshold) {
  c.set("fields/temperature/doubleValue", isnan(temperature) ? 0 : temperature);
  c.set("fields/humidity/doubleValue", isnan(humidity) ? 0 : humidity);
  c.set("fields/ldr/integerValue", String(ldrValue));
  c.set("fields/bulbState/booleanValue", bulbState);
  c.set("fields/mode/stringValue", mode);
  if (withThreshold) c.set("fields/threshold/integerValue", String(threshold));
  c.set("fields/timestamp/timestampValue", isoTimestamp());
}

void updateCurrent() {
  FirebaseJson c;
  fillFields(c, true);
  if (!Firebase.Firestore.patchDocument(&fbdo, FIREBASE_PROJECT_ID, "", "sensors/current", c.raw(),
                                        "temperature,humidity,ldr,bulbState,mode,threshold,timestamp")) {
    Serial.println("sensors/current write failed: " + fbdo.errorReason());
  }
}

void appendLog() {
  FirebaseJson c;
  fillFields(c, false);

  // Readable, unique-per-3-minutes ID in local time: "sep11_1745"
  time_t now;
  time(&now);
  char id[16];
  strftime(id, sizeof(id), "%b%d_%H%M", localtime(&now));
  for (char* p = id; *p; p++) *p = tolower(*p);
  String path = "readings/" + String(id);
  if (Firebase.Firestore.createDocument(&fbdo, FIREBASE_PROJECT_ID, "", path.c_str(), c.raw())) {
    Serial.println("Logged -> " + path);
  } else {
    Serial.println("Log write failed: " + fbdo.errorReason());
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  setBulb(false);
  analogReadResolution(12);
  dht.begin();

  WiFi.begin(WIFI_SSID, WIFI_PASSWORD);
  Serial.print("Connecting to Wi-Fi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(300);
    Serial.print(".");
  }
  Serial.println("\nWi-Fi connected: " + WiFi.localIP().toString());

  // IST (UTC+5:30) so reading IDs use local time; timestamps stay in UTC
  configTime(19800, 0, "pool.ntp.org", "time.google.com");
  Serial.print("Syncing time");
  while (time(nullptr) < 1700000000) {
    delay(300);
    Serial.print(".");
  }
  Serial.println(" done");

  config.api_key = API_KEY;
  auth.user.email = DEVICE_EMAIL;
  auth.user.password = DEVICE_PASSWORD;
  config.token_status_callback = tokenStatusCallback;
  Firebase.begin(&config, &auth);
  Firebase.reconnectWiFi(true);
}

void loop() {
  if (!Firebase.ready()) return;
  unsigned long now = millis();

  if (now - lastControl >= CONTROL_MS) {
    lastControl = now;
    Serial.println("\nChecking Firebase control...");
    readSensors();
    readControl();
    applyLogic();
  }

  if (now - lastSensor >= SENSOR_MS) {
    lastSensor = now;
    updateCurrent();
  }

  if (now - lastLog >= LOG_MS) {
    lastLog = now;
    appendLog();
  }
}

Problems Encountered & Solutions

Problem: The relay chattered (clicked on and off quickly) when the light level was close to the threshold.

Solution: Replaced the single threshold with darkLimit / brightLimit (±50) and averaged 10 ADC samples per reading. The Serial Monitor log shows the new limits.

Problem: The Sensor History table showed "No historical data available".

Solution: The firmware only overwrote sensors/current, so there was no history to show. I added an append-only readings collection that gets a new entry every 3 minutes (sep11_1745, sep11_1748, …), and the dashboard reads that collection.

Problem: Analog readings stopped working on some pins once Wi-Fi connected.

Solution: ADC2 is shared with the Wi-Fi radio. I moved the LDR to GPIO34, which is on ADC1.

Problem: The first log entries had a 1970 timestamp.

Solution: The ESP32 had no clock yet. setup() now waits for NTP time before it starts logging.

Limitations of the Current Prototype

  • The ESP32 polls Firestore every 2 s, so commands can take up to 2 s, and the reads count against the free-tier quota.
  • The DHT11 is coarse (±2 °C, ±5 % RH, whole numbers only). The LDR gives relative brightness, not calibrated lux.
  • No offline buffering: readings taken while Wi-Fi is down are lost, not uploaded later.
  • Every signed-in user has the same access. There are no roles (admin / viewer) or per-device ownership.
  • The relay is switching mains on a breadboard prototype with no enclosure or fuse. It is not safe for permanent use.

Possible Future Improvements

  • Replace polling with a Firestore stream, or MQTT, for instant commands and fewer reads.
  • Use a DHT22/BME280 and a BH1750 lux sensor for accurate, calibrated readings.
  • Store readings on the device (SPIFFS/LittleFS) during outages and upload them on reconnect.
  • Role-based rules (custom claims) and multi-device support under each user account.
  • Alerts (email/push) when temperature crosses a limit, plus scheduled lighting.
  • A Cloud Function to delete readings older than 30 days, and a date-range picker for CSV export.

I also learned that "automatic" control still needs a person to calibrate it, and that small details like hysteresis, ADC pin choice and clock sync decide whether a prototype is reliable.
