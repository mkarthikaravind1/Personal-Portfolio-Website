IoT Experiment 1

Blinking an LED on ESP32

The starting point of the whole sequence — programming the ESP32 to blink an onboard LED. It's a small result on its own, but it confirms the board setup, GPIO control, and toolchain that every later experiment builds on top of.

code upload → GPIO write → LED response

Components & Hardware

ESP32 DevKit V4
Main microcontroller
USB Cable
Power & programming link
Arduino IDE
Firmware upload

How I Built This

  1. Install the toolchain. Arduino IDE, plus ESP32 board support added through the Boards Manager.
  2. Select board & port. Tools → Board → ESP32 Dev Module, then pick the correct serial port.
  3. Upload the sketch. Paste the code below and hit Upload.
  4. Verify the result. Watch the onboard LED blink, and check Serial Monitor at 115200 baud if it doesn't.
Wiring: none needed — this uses the LED already wired to the board.

Source Code

exp1_led_blink.ino
// Experiment 1 — Blinking an LED on ESP32
#define LED_PIN 2   // Onboard LED on most ESP32 DevKit boards

void setup() {
  pinMode(LED_PIN, OUTPUT);
  Serial.begin(115200);
}

void loop() {
  digitalWrite(LED_PIN, HIGH);
  Serial.println("LED ON");
  delay(500);

  digitalWrite(LED_PIN, LOW);
  Serial.println("LED OFF");
  delay(500);
}

IoT Experiment 2

Bulb Control via Locally Hosted Website

Control moves off the board and onto a page a person can actually click. The ESP32 hosts a lightweight website on the local network using Arduino, and toggling a button there switches a bulb connected through the board.

browser click → local Wi-Fi request → ESP32 → relay → bulb

Components & Hardware

ESP32 DevKit V4
Runs the web server
5V Relay Module
Switches the bulb
Bulb & Holder
The load being switched
Local Wi-Fi (2.4GHz)
Connects browser to board

How I Built This

  1. Wire the relay. IN to a GPIO, VCC/GND to power, COM/NO in line with the bulb's live wire.
  2. Connect to Wi-Fi. Add the SSID/password to the sketch and confirm the assigned IP over Serial.
  3. Start the web server. WebServer.h listens on port 80 and exposes /api/on and /api/off.
  4. Build the control page. A small HTML page with ON/OFF buttons that call those endpoints.
  5. Test it. Load the ESP32's IP from a browser on the same network and toggle the bulb.
Wiring note: this is the first experiment with mains-adjacent wiring. The relay's low-voltage side (VCC / GND / IN) connects to the ESP32; its high-voltage side (COM / NO) sits in series with the bulb's live wire. Always wire and check this side with the bulb unplugged from the wall first.

Source Code

exp2_local_web_control.ino
// Experiment 2 — Bulb control via a locally hosted website
#include <WiFi.h>
#include <WebServer.h>

const char* ssid     = "YOUR_WIFI_SSID";
const char* password = "YOUR_WIFI_PASSWORD";

#define RELAY_PIN 26
WebServer server(80);
bool bulbState = false;

const char* page = R"rawliteral(
<!DOCTYPE html><html><body style="font-family:sans-serif;text-align:center;margin-top:60px;">
<h2>Bulb Control</h2>
<button onclick="fetch('/api/on')">Turn ON</button>
<button onclick="fetch('/api/off')">Turn OFF</button>
</body></html>
)rawliteral";

void handleRoot() { server.send(200, "text/html", page); }

void handleOn() {
  digitalWrite(RELAY_PIN, HIGH);
  bulbState = true;
  server.send(200, "text/plain", "ON");
}

void handleOff() {
  digitalWrite(RELAY_PIN, LOW);
  bulbState = false;
  server.send(200, "text/plain", "OFF");
}

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, LOW);

  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("\nIP address: " + WiFi.localIP().toString());

  server.on("/", handleRoot);
  server.on("/api/on", handleOn);
  server.on("/api/off", handleOff);
  server.begin();
}

void loop() {
  server.handleClient();
}

IoT Experiment 3

Bulb Control via Google Voice Assistant

The same bulb from Experiment 2, but the trigger is now spoken instead of clicked. A Google Voice Assistant command gets routed through IFTTT to the existing local website, so the hardware side stayed untouched — only the way a command reaches it changed.

voice command → Google Assistant → IFTTT → ESP32 endpoint → bulb

Same ESP32 + Relay Setup
Reused from Experiment 2

How I Built This

  1. Create an IFTTT applet. Trigger: Google Assistant, with a phrase like "turn on the bulb".
  2. Set the action to Webhooks. Point it at the ESP32's /api/on endpoint from Experiment 2.
  3. Repeat for OFF. A second applet with the OFF phrase pointed at /api/off.
  4. Test end-to-end. Say the command and confirm the bulb switches, checking Serial Monitor for the incoming request.
Wiring: unchanged — this experiment reuses Experiment 2's relay and bulb wiring exactly. Nothing new to connect.

IoT Experiment 4

Bulb Control via Firebase-Connected Website

Local control becomes remote control. The bulb is now switched through a website backed by Firebase, with the ESP32 watching the cloud database for state changes instead of only listening on the local network — reachable from anywhere, not just the same Wi-Fi.

website → Firebase Realtime Database → ESP32 stream → relay → bulb

Components & Hardware

ESP32 DevKit V4
Streams DB state
Relay + Bulb
Reused from Exp. 2
Firebase Project
Realtime Database

How I Built This

  1. Create a Firebase project. Enable the Realtime Database and grab the API key and database URL.
  2. Add Firebase to the sketch. Firebase_ESP_Client.h with the project credentials.
  3. Stream a database path. Listen on /appliances/bulbState for changes.
  4. Drive the relay from that value. Update the GPIO whenever the streamed value changes.
  5. Build the web front end. A page that writes true/false to that same path.
Wiring: identical to Experiment 2's relay/bulb circuit — this step changes the software path only.

Source Code

exp4_firebase_control.ino
// Experiment 4 — Bulb control via a Firebase-connected website
#include <WiFi.h>
#include <Firebase_ESP_Client.h>

#define WIFI_SSID     "YOUR_WIFI_SSID"
#define WIFI_PASSWORD "YOUR_WIFI_PASSWORD"
#define API_KEY       "YOUR_FIREBASE_API_KEY"
#define DATABASE_URL  "YOUR_PROJECT.firebaseio.com"

#define RELAY_PIN 26

FirebaseData fbdo;
FirebaseAuth auth;
FirebaseConfig config;
bool bulbState = false;

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);

  WiFi.begin(WIFI_SSID, WIFI_PASSWORD);
  while (WiFi.status() != WL_CONNECTED) delay(300);

  config.api_key = API_KEY;
  config.database_url = DATABASE_URL;
  Firebase.begin(&config, &auth);
  Firebase.RTDB.beginStream(&fbdo, "/appliances/bulbState");
}

void loop() {
  if (Firebase.RTDB.readStream(&fbdo) && fbdo.streamAvailable()) {
    bulbState = fbdo.to<bool>();
    digitalWrite(RELAY_PIN, bulbState ? HIGH : LOW);
    Serial.println(bulbState ? "Bulb -> ON" : "Bulb -> OFF");
  }
}

IoT Experiment 5

Bulb Automation via LDR Sensor

The closing experiment takes the person out of the loop. An LDR reads ambient light and the board decides on its own whether the bulb should be on — no button, no voice command, no remote trigger, just the system responding to its environment. Every earlier experiment needed a human or a cloud request to act as the trigger; this one closes the loop entirely on-device.

ambient light → LDR reading → threshold check → relay → bulb

Learning Objectives

  • Read a continuous analog signal instead of reacting to a single discrete event
  • Convert a raw ADC value into a simple on/off decision using a threshold
  • Reuse an existing actuator (the Experiment 2 relay) with an entirely new trigger source
  • Understand why threshold-based automation still needs a person to calibrate it once

Components & Hardware

ESP32 DevKit V4
Reads & decides
LDR Module
Ambient light sensor
Relay + Bulb
Reused from Exp. 2
Key specifications — LDR module: analog light sensor · output range 0–4095 on the ESP32's 12-bit ADC · higher reading means a darker room · powered from 3.3V · not a calibrated lux value, just a relative brightness reading.

Wiring Architecture

wiring_diagram.txt
            ESP32 DevKit
          ┌───────────────────┐
          │                   │
  LDR AO ─┤ GPIO34 (ADC-only) │
  LDR VCC ┤ 3.3V              │
  LDR GND ┤ GND               │
          │                   │
          │ GPIO26 ───────────┼──── Relay IN
          └───────────────────┘
                                Relay COM/NO → Bulb
                                (same circuit as Experiment 2)

How I Built This

  1. Wire the LDR. Analog output to an ADC-capable GPIO, power from 3.3V.
  2. Read ambient light. Sample the analog value on a short interval.
  3. Set a threshold. Decide the raw reading that counts as "dark enough".
  4. Drive the relay from that threshold. No manual input from here on.
Wiring note: the LDR module's analog output goes to GPIO34, an input-only ADC pin on the ESP32; VCC and GND go to 3.3V and ground. The relay/bulb side is unchanged from Experiment 2.

Source Code

exp5_ldr_automation.ino
// Experiment 5 — Bulb automation via an LDR sensor
#define LDR_PIN   34   // ADC-only input pin
#define RELAY_PIN 26

int threshold  = 2500;  // tune to the room's lighting
int hysteresis = 150;   // gap around the threshold so the relay doesn't chatter
bool bulbState = false;

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, LOW);
  Serial.println("LDR automation ready.");
  Serial.printf("Threshold: %d (+/- %d)\n", threshold, hysteresis);
}

void loop() {
  int lightLevel = analogRead(LDR_PIN);

  if (!bulbState && lightLevel > threshold + hysteresis) {
    bulbState = true;
    digitalWrite(RELAY_PIN, HIGH);
  } else if (bulbState && lightLevel < threshold - hysteresis) {
    bulbState = false;
    digitalWrite(RELAY_PIN, LOW);
  }

  Serial.printf("LDR: %d -> Bulb %s\n", lightLevel, bulbState ? "ON" : "OFF");
  delay(500);
}

Code Breakdown

  • analogRead(LDR_PIN) — reads the raw light level from the 12-bit ADC (0–4095)
  • threshold — the raw value that separates "dark enough" from "bright enough"; tuned by trial and error for the room it sits in
  • hysteresis — a small buffer zone around the threshold so a reading hovering right at the line doesn't flip the relay on and off repeatedly
  • bulbState — tracked in code rather than re-derived every loop, so the hysteresis check has something to compare against
  • digitalWrite(RELAY_PIN, ...) — drives the exact relay wired in Experiment 2
  • delay(500) — a simple 500 ms sampling interval; no interrupts needed for a signal that changes this slowly

Project

ESP32 OLED Display & Ultrasonic Game

Two smaller pieces built in one session: rendering our team number on an I2C OLED display, then a short reaction-based game driven by live ultrasonic distance readings — display interfacing and real-time sensor input in the same sketch.

ultrasonic pulse → echo timing → distance → OLED output

Components & Hardware

ESP32 DevKit V4
Runs display + sensor
SSD1306 OLED (I2C)
128×64 display
HC-SR04 Ultrasonic
Distance sensor

How I Built This

  1. Wire the OLED over I2C. SDA/SCL to the ESP32's default I2C pins.
  2. Wire the ultrasonic sensor. Trig and Echo to two free digital GPIOs.
  3. Display the team number. Render "24" on the OLED at startup.
  4. Read live distance. Trigger a pulse and time the echo to get distance in cm.
  5. Turn distance into gameplay. Map a distance threshold into simple reaction feedback on the display.
Wiring note: the OLED uses the ESP32's default I2C pins (SDA on GPIO21, SCL on GPIO22). The HC-SR04's Echo pin outputs 5V — a voltage divider or level shifter protects the ESP32's 3.3V-only GPIO if you're running it from 5V.

Source Code

oled_ultrasonic_game.ino
// Project — ESP32 OLED Display & Ultrasonic Reaction Game
#include <Wire.h>
#include <Adafruit_SSD1306.h>

#define TRIG_PIN 5
#define ECHO_PIN 18
#define SCREEN_WIDTH 128
#define SCREEN_HEIGHT 64

Adafruit_SSD1306 display(SCREEN_WIDTH, SCREEN_HEIGHT, &Wire, -1);

long readDistanceCM() {
  digitalWrite(TRIG_PIN, LOW);  delayMicroseconds(2);
  digitalWrite(TRIG_PIN, HIGH); delayMicroseconds(10);
  digitalWrite(TRIG_PIN, LOW);
  long duration = pulseIn(ECHO_PIN, HIGH);
  return duration * 0.034 / 2;
}

void setup() {
  Serial.begin(115200);
  pinMode(TRIG_PIN, OUTPUT);
  pinMode(ECHO_PIN, INPUT);

  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  display.clearDisplay();
  display.setTextSize(3);
  display.setTextColor(SSD1306_WHITE);
  display.setCursor(30, 20);
  display.print("24");
  display.display();
  delay(1500);
}

void loop() {
  long distance = readDistanceCM();

  display.clearDisplay();
  display.setTextSize(2);
  display.setCursor(0, 0);
  display.print(distance);
  display.println(" cm");

  if (distance < 10) {
    display.setTextSize(1);
    display.setCursor(0, 40);
    display.print("Hit!");
  }
  display.display();
  delay(150);
}

Reflection

What this run taught me

  • The ESP32 turned out to be genuinely multi-purpose — display output, sensor input, and wireless control all on the same board across these builds.
  • Going local control → voice control → cloud control → sensor automation made it clear that connected products add complexity in layers, not all at once.
  • FreeRTOS task notifications are a much cleaner way to signal between tasks than shared variables — there's no race condition to reason about.
  • Setting the timing budget — sampling rate, alert deadline, jitter tolerance — before writing any code forced far more precision than starting from the code itself.
